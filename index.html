An AI agent's paid calls, each one costed and capped before it goes out.

Kar, the resident builder of a large private software estate, has a small amount of Claude API credit to spend on its hardest thinking. This is the wall in front of that credit. A request must show that the cheaper ways were tried and failed. Before it can go out, the wall reserves the most that request could possibly cost, against a daily cap and a hard stop. Afterwards it settles the call at what the API says it cost. Every attempt it handles gets a numbered line in a ledger, and kar-tally, a separate checker from the same estate, re-adds the ledger in order, so a deleted line shows.

What this is

A small piece of plumbing between an AI agent and a paid model API. The agent may use the paid model only when the job reports that its free tools and its own local model failed. Before a request goes out, the wall works out the most it could cost and reserves that against the day's cap and a hard stop; a request that would not fit is refused, with the reason, and nothing is sent. After the answer, the call is priced from the usage the API reported and the reservation comes down to that. Nothing is sent that was not reserved first.

Its first job is Kar's pattern library. Every night a local 7-billion-parameter model on the laptop writes rules that sort Kar's repositories into families, and a strict gate keeps only rules that win on data they never saw. When the local model fails a family completely, that family may go to Claude with the very same question, and Claude's rules face the very same gate. Once a rule Claude wrote for a family passes, the library covers that family and it is never sent again.

Who it stops, and who it does not

It stops mistakes and runaway code: a loop that runs all night, a retry storm, a prompt that grows without anyone noticing, a job that reaches for the expensive model when a cheap one would do, a process that dies halfway through a call. Those are the ways spend usually gets away from a team, and the wall answers each one before the money goes.

It does not stop someone, or something, that can already write to your files. Whoever can read the key file can call the API directly; whoever can edit the settings file can raise the stop; whoever can delete the ledger can start again. That is why the provider's own limit stays on as the outer wall (turn auto-reload off, or set a spend limit in the Console), and why the ledger is numbered and re-added: tampering inside it shows, though deleting the whole file does not.

Start here

  1. Get the code. Clone the repository and run npm ci with Node 22 (the version CI tests). There is one dependency, Anthropic's official SDK, pinned to an exact version.
  2. Put the key in a file, not in the environment. Save the API key alone in ~/.si-didy/keys/anthropic-api.key, outside every repository, readable only by you. For real calls the wire reads the key from there and the ledger from ~/.si-didy/api/; no environment variable can move either, and every ANTHROPIC_* variable is removed from its process.
  3. Keep the provider's own limit on. Turn auto-reload off in the Anthropic Console, or set a spend limit. That outer wall holds even if this machine is compromised.
  4. Set your numbers, if you want different ones. Write them to ~/.si-didy/api/settings.json, in cents, for example {"dayCents": 300, "stopCents": 9500}. A stop above the default credit needs the credit too: {"stopCents": 19000, "creditCents": 20000}.
  5. Send a request. Pipe one JSON line to node tools/ask.mjs, and read one JSON line back: 
    in:  {"job": "teacher", "prompt": "...", "system": "(optional)",
      "evidence": {"tier1": {"asked": true, "answered": false},
                   "tier2": {"tried": 3, "passed": 0}}}
out: {"ok": true, "code": "end_turn", "text": "...", "seq": 12,
      "costCents": 3, "ceilingCents": 14, "brief": "the morning line"}
     or {"ok": false, "code": "day", "why": "API budget reached for today ...", ...}
  6. Read the ledger. node tools/audit.mjs judges the real ledger by the claims' own bars and has kar-tally re-add it; --write saves the result as the receipt this page shows.

    What it will not do

    • It will not send a request whose evidence does not say the cheaper tiers were tried and failed. It trusts what the job reports, and keeps that evidence in the ledger for anyone to check.
    • It will not send a request before its whole worst case is reserved on disk.
    • It will not retry: a retry would be a second spend under one reservation.
    • It will not guess a price. A model with no flat published price is refused.
    • It will not take a credential or an address from its environment for a real call. The real key goes only to Anthropic's API; the test mode refuses to read it.
    • It will not act on an answer. It returns text; the job's own gate decides what it is worth.
    • It will not pass the stop, or switch itself back on: that takes raising the stop in the settings file.
    • It does one prompt in, text out. No tools, images, streaming or conversations: the first job needs none of them.

    Adoption

    Any team that lets software call a paid model has the same exposure. Dashboards tell you afterwards. The provider's limits are enforced, but per organisation or workspace and by the month. This wall decides before each call, per ledger and per UTC day, and writes down why.

    • Put it in front of one job first. One ledger, one cap; the morning line reports spend by job. Watch it for a week.
    • Write the evidence your cheaper path produces. The tier order is only as honest as the evidence passed in; build it from your job's own records, not from anything a model says.
    • Keep the provider's own limit as the outer wall. Two walls, one of them outside your machine.
    • Audit the real ledger. Run tools/audit.mjs daily and compare its total with the provider's usage page now and then: the checker proves the ledger adds up and has no gaps; the usage page proves nothing was spent outside it.

    A pilot, step by step

    1. Pick the job. One automated job that calls a paid model today.
    2. Set the cap from the bill you can live with. The calculator below shows what a runaway loop would cost with the wall and without it.
    3. Wire the job through tools/ask.mjs. Pass the evidence of what the cheap path tried.
    4. Run for two weeks. Read the morning line daily; run the audit.
    5. Compare with the provider's usage page. The wall's total should be at or above the provider's: it rounds every call up to the cent, and charges a failed call its whole ceiling.
    6. Decide. Keep it, widen it to a second job, or take it out. Nothing else changes.

    White paper: reserve before you spend

    The problem. A spend control that looks only at what has been spent so far, and refuses once a limit is crossed, is too late by one call, and a model call can be expensive: the output alone can run to tens of thousands of tokens, thinking included. A loop that checks the balance and then makes a large call can overshoot by the size of that call, every day.

    The idea. Bound the call before it exists. Take its input as no more tokens than it has bytes, plus an allowance, and its output as the full limit you set; that is the most it can cost. Reserve that whole amount against the cap, on disk, before the request goes out. When the answer comes back, settle it at what it really cost. If the process dies mid-call, the reservation stands, so the ledger never under-counts. A single call too big for any whole day is refused on its own, without touching the stop.

    The order. A paid call is the last resort. The request must carry evidence that the free tools and the local model were tried and failed, and the wall refuses it otherwise.

    The stop. A hard stop a little under the credit, so a call never meets an empty balance mid-flight. When a call is refused there, the tier latches off: it does not drift back on as small calls fit again.

    The proof. Every decision lives in one pure file, and the mutation gate caught every change it made to it. Sixty days of hostile demand run through that same file and are re-derived on every push. kar-tally re-adds the numbered ledger. The wire is tested end to end against a stand-in API with decoy credentials in its environment. The real ledger is judged every morning by the same rules.

    The honest limits. kar-tally proves the ledger adds up and has no gaps, not that it is complete: deleting its last lines, or the whole file, does not show, so compare it with the provider's usage page. The one-token-per-byte bound is an assumption about Anthropic's tokenizer; the audit checks it on every real answer, and the simulation, which never breaks it by design, cannot test it. Prices are read from the provider's page by hand, with the date; if they change, the table must be updated.

    Security, compliance and data

    • For a real call the key is read from one fixed file by one process and sent only to Anthropic's API; it is never written to the ledger, the console or the page. A test proves it with a fake key and decoy credentials; CI scans every tracked file for anything shaped like a key.
    • The ledger holds job names, sizes, token counts, costs, the evidence in its fixed shape, and the API's error text when a call fails. It holds no prompt and no answer.
    • The page loads only its own files and sends nothing anywhere.

    Risks, answered straight

    Can the agent go around the wall?An agent that can run commands as you can read the key file or edit the settings. The wall stops mistakes and runaway code, not that; the provider's own limit is the wall it cannot touch.
    What if the price changes?The price table names its source and the date it was read. Update it the day prices change. Rounding every charge up gives a little slack, not a guarantee.
    What if a call costs more than its ceiling?It is still charged in full and flagged as an overrun in the ledger and the morning line. Loading…
    What if the process dies mid-call?The reservation is already on disk, so the call counts at its whole ceiling. A lock left behind clears itself after ten minutes. A second call that finds the lock held is turned away before it reaches the ledger.
    Can the job lie about the evidence?Yes: the wall trusts what the job reports. The evidence is kept in the ledger with every call, for anyone to check, and Kar's teacher builds it from the night's own records, never from anything a model says.
