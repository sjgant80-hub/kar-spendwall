An AI agent's paid calls, behind a wall it cannot climb.

Kar, the estate's resident builder, has about a hundred dollars of Claude API credit to spend on its hardest thinking. Everything cheaper goes first. Before a request can go out, this wall reserves the most that call could possibly cost, against a daily cap and a hard stop. Afterwards it settles the call at what it really cost. Every attempt goes in a ledger, and a separate auditor re-adds it.

What this is

A small, proven piece of plumbing that sits between an AI agent and a paid model API. The agent uses the paid model only when its free tools and its own local model have genuinely failed. Before any request goes out, the wall works out the worst case that request could cost and reserves it against the day's cap and a hard stop; a request that would not fit is refused, and the work carries on locally. After the answer comes back, the call is priced from what the API reported and the reservation is released down to that. Nothing can spend that was not reserved first.

The one job it serves first is Kar's pattern library. Every night a local 7-billion-parameter model on the laptop tries to write rules that sort Kar's repositories into families, and a strict gate keeps only rules that win on data they never saw. When the 7B fails a family completely, that family, and only that family, may go to Claude with the very same question. Claude's rules face the very same gate. A family Claude teaches is covered from then on, so the same question never costs twice.

Words on this page

API
The paid service a program calls to use a large model, here Anthropic's Claude. It bills by the token.
Token
The unit a model reads and writes, a few letters long. A token is never shorter than one byte, which is what lets the wall bound a request's cost before it is sent.
Tier 1, 2, 3
The order of who does the work: tier 1 is free deterministic tools and the pattern library; tier 2 is the local 7B; tier 3 is the paid API. The last word, on anything public, paid or risky, is Simon's.
The 7B
A 7-billion-parameter model (qwen2.5:7b) that runs on the laptop itself, for free.
Pattern library
Kar's growing set of small, proven rules (WHEN a word THEN a family), each kept only after winning on held-out data.
The gate
The deterministic test every rule must pass to enter the library, whoever wrote it.
Ceiling
The most one call could cost: every byte of the request priced as a token at the dearer input price, plus a framing allowance, plus every output token the limit allows. Rounded up to a whole cent.
Reservation
The ledger line written, and flushed to disk, before a request goes out. It charges the whole ceiling.
Settle
The ledger line written after the answer: the call priced from the usage the API reported, rounded up to the cent. An unreadable answer is charged the whole ceiling.
Daily cap
The most the tier may spend in one UTC day.
The stop
The total Kar will not pass, set a little under the credit so a call never meets an empty balance mid-flight. Once a call is refused there, the tier stays off until Simon raises the stop.
UTC day
A day by the world clock, midnight to midnight, not by the laptop's time zone.
Ledger
The append-only file of every attempt: reservations, settlements and refusals, each with its reason.
kar-tally
A separate auditor from the same estate. It re-adds a spend log from scratch and checks that the running balance never went below zero. It is used here unmodified.
Mutation gate
witness: it changes the code one operator at a time and checks the tests catch every change. "Clean" means every change was caught.

Start here

  1. Get the code. Clone the repository and run npm ci. There is one dependency, Anthropic's official SDK, pinned to an exact version.
  2. Put the key in a file, not in the environment. Save the API key alone in ~/.si-didy/keys/anthropic-api.key, outside every repository. The wire reads it from there and nowhere else, and removes every ANTHROPIC_* variable from its own process.
  3. Turn auto-reload off in the Anthropic Console. Then the credit itself is a hard stop that no bug in any code can pass. The wall's stop sits just under it.
  4. Set your numbers, if you want different ones. Write {"dayCents": 300, "stopCents": 9500} to ~/.si-didy/api/settings.json. Leave the file out for Kar's defaults.
  5. Send a request. Pipe one JSON line to node tools/ask.mjs: the job, the evidence that the cheaper tiers failed, and the prompt. You get one JSON line back: the answer or the refusal, the cost, and the morning line.
  6. Read the ledger. node tools/audit.mjs judges the real ledger by the claims' own bars and has kar-tally re-add it.

    What it will not do

    • It will not call the API for a job the free tiers could do, or without the evidence that they failed.
    • It will not send a request before its whole worst case is reserved on disk.
    • It will not retry: a retry would be a second spend under one reservation.
    • It will not guess a price. A model with no published flat price is refused.
    • It will not read a credential or an endpoint from its environment, or send the key anywhere but Anthropic's API.
    • It will not let an answer act on its own: an answer is a proposal until the job's own gate passes it.
    • It will not pass the stop, or switch itself back on. Only Simon raising the stop does that.

    Adoption

    Any team that lets software call a paid model has the same exposure: a loop that runs all night, a retry storm, a prompt that grows without anyone noticing. Provider dashboards and monthly limits tell you afterwards, for the whole organisation at once. This wall decides before each call, for each job, and writes down why.

    • Put it in front of one job first. One script, one ledger, one cap. Watch the morning line for a week.
    • Write the evidence your cheaper tiers produce. The tier order is only as honest as the evidence passed in; make the job record what the cheap path tried.
    • Keep the provider's own limit as the outer wall. Auto-reload off, or a spend limit in the Console. Two walls, one of them outside your code.
    • Audit the real ledger. Run tools/audit.mjs daily, and compare its total with the provider's usage page now and then: the auditor proves the ledger adds up, and the usage page proves the ledger is complete.

    A pilot, step by step

    1. Pick the job. One automated job that calls a paid model today.
    2. Set the cap from the bill you can live with. The page's calculator below shows the runway it gives you.
    3. Wire the job through tools/ask.mjs. Pass the evidence of what the cheap path tried.
    4. Run for two weeks. Read the morning line daily; run the audit.
    5. Compare with the provider's usage page. The wall's total should sit at, or a little above, the provider's: it rounds every call up to the next cent.
    6. Decide. Keep it, widen it to a second job, or take it out. Nothing else changes.

    White paper: reserve before you spend

    The problem. A spend control that looks only at what has been spent so far, and refuses once a limit is crossed, is too late by one call, and a model call can be expensive: the output alone can run to tens of thousands of tokens, thinking included. A loop that checks the balance and then makes a large call can overshoot by the size of that call, every time.

    The idea. Bound the call before it exists. A request's input cannot be more tokens than it has bytes, and its output cannot exceed the limit you set. So the most it can cost is known in advance. Reserve that whole amount against the cap, on disk, before the request goes out. When the answer comes back, settle it at what it really cost and release the rest. If the process dies mid-call, the reservation stands, so the ledger never under-counts.

    The order. A paid call is the last resort, not the default. The request must carry evidence that the free tools and the local model were tried and failed. The wall refuses it otherwise.

    The stop. A hard stop a little under the credit, so a call never meets an empty balance mid-flight. When a call is refused there, the tier latches off. It does not drift back on as small calls fit again; a person turns it back on.

    The proof. Every decision lives in one pure file that the mutation gate proves: every change to it is caught by a test. Sixty days of hostile demand run through that same file and are re-derived on every push. An auditor from outside the build re-adds the ledger. The live wire is tested end to end against a stand-in API with decoy credentials in its environment. The real ledger is audited every morning by the same rules.

    The honest limits. The auditor proves the ledger adds up, not that it is complete: compare it with the provider's usage page. Prices are read from the provider's page by hand, with the date; if they change, the table must be updated. A token is never shorter than a byte, but the framing allowance is still an allowance: the record counts overruns, the morning brief checks the real ledger for them every day, and so far there have been none.

    Security, compliance and data

    • The key is read from one file outside every repository, by one process, sent to one address, and never written to the ledger, the console or the page. A test proves it with a fake key and decoy credentials; CI scans every tracked file for anything shaped like a key.
    • The ledger holds job names, sizes, token counts and costs. It holds no prompt and no answer.
    • The page loads only its own files. It sends nothing anywhere.

    Risks, answered straight

    What if the price changes?The price table names its source and the date it was read. Update it the day prices change; until then, the wall prices by the old table. Rounding every charge up gives a little slack, not a guarantee.
    What if a call costs more than its ceiling?It is still charged in full and flagged as an overrun in the ledger and the morning line. Loading…
    What if the process dies mid-call?The reservation is already on disk, so the call counts at its whole ceiling. A lock left behind clears itself after ten minutes.
    Can the agent forge the evidence?The wall trusts the evidence the job writes. That is why the evidence is kept in the ledger with every call, for anyone to check, and why the teacher job builds it from the night's own records rather than from anything the model says.
